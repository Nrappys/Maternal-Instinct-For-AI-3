- role child ห้าม GATHER ทุกวัยใน Episode แต่กินอาหารที่มี พัก เล่น เคลื่อนที่ และสื่อสารได้ แม่ต้องจัดหาอาหารผ่าน FEED จึงอยู่รอดได้อย่างต่อเนื่อง การเปลี่ยน role เป็น mother ของผู้รอดที่ได้รับคัดเลือกในรุ่นถัดไปจึงเปิด GATHER

- แม่และลูกมีความเสี่ยงตายจาก physiology ตามเดิม ไม่เขียน child.hp=0 เมื่อแม่ตาย บันทึกเวลาที่ไม่มีแม่ การตายหลังแม่ และการยังมีชีวิตเมื่อแม่ตายใกล้หมดเวลา การเสียแม่ใกล้จบไม่รับประกันว่าลูกจะหมด Food/Health ภายในเวลาที่เหลือ

- ยังไม่ได้รันตรวจสมดุลจริง ตรวจเฉพาะโครงสร้าง/คำนวณ ไม่มีการเริ่ม Simulation การประเมิน เทรน หรือ unit tests อัตโนมัติ ผลกติกาเก่าไม่รวมกับกติกาใหม่นี้

# ข้อกำหนดปัจจุบันหลังปรับสมดุล

กติกาปัจจุบัน `maternal-house-v2.1-balanced` และข้อสอบ `full_lifetime_care_v2_balanced` อยู่ในโปรเจกต์เดิม

- ลูกพึ่งแม่ก่อนอายุ 7 วัน; เริ่มทำเอง 7–14 วัน; เต็มขีดความสามารถตั้งแต่ 14 วัน ใช้พารามิเตอร์เดียวกันใน physics, ช่วงวัยรายงาน และการนัดเหตุการณ์ข้อสอบ
- Food ลดต่อ Step: แม่ 0.03, ลูกเล็ก 0.12, ช่วงเริ่มทำเอง 0.07, ช่วงโต 0.05
- หิวต่ำกว่า 20 เกิน 40 Steps เสีย Health 0.08/Step; เหนื่อย/เครียดสูงกว่า 90 เกิน 40 Steps เสียอย่างละ 0.01/Step; อาหาร +30, การพัก, การฟื้น Health, อันตราย และขนาดโลกเหมือนเดิม
- ไม่เพิ่มโรค/ความหนาว/โอกาสตายสุ่ม ไม่เพิ่ม Reward RL แม่จากการเลี้ยงลูก
- Fitness เปลี่ยนเป็น survival × (0.5 + 0.3 × full-life child Health/100 + 0.2 × solo score) จึงแยกผู้รอดที่สุขภาพต่างกันได้ ไม่ใช้ Zero-shot คัดเลือก เกณฑ์สุขภาพเป็นเป้าหมายที่ผู้ออกแบบกำหนดโดยตรง ต้องรายงานตามจริง
- A0 normal มี learned, no_help, appropriate_help, always_help กฎอ้างอิงไม่ใช่การเทรนโมเดลเพิ่มเติม ไม่อ้างว่า optimal หรือมีข้อมูลเท่า policy
- หัวข้อ 1.1 มีปุ่ม Check balance เริ่มด้วยการกดเองเท่านั้น ตรวจชีวิตปกติและข้อสอบด้วยกฎสามแบบโดยไม่โหลดโมเดล ผลอยู่ outputs/full_lifetime/balance_check_... พร้อม config และ source hashes หากหยุดกลางงาน metadata จะไม่เป็น completed
- ผลกติกาเก่าเก็บไว้ตามจริง ไม่โหลด checkpoint มารันต่อในโลกใหม่และไม่รวมผลเปรียบเทียบ ข้อความด้านล่างเป็นประวัติการออกแบบก่อนปรับสมดุล หากขัดกับส่วนนี้ ให้ยึดส่วนนี้และ README ปัจจุบัน
- ตรวจ syntax/โครงสร้างและคำนวณสเกลเวลาเท่านั้น ยังไม่ได้รันตรวจสมดุลจริง จึงไม่รับประกันการรอดของกฎอ้างอิงหรือการไม่สูญพันธุ์ของประชากรเริ่มต้น

ตัวอย่างคำนวณจากพารามิเตอร์ ไม่ใช่ผลรัน: ลูกที่ Food เริ่ม 70 และอยู่นิ่ง ใช้ประมาณ 417 Steps จนต่ำกว่า 20 หากไม่ได้อาหารจนถึงอายุ 7 วัน จะเสีย Health จากความหิวประมาณ 75 หน่วยก่อนเริ่มหยิบอาหารเอง ลูกที่ Food เริ่ม 20 และไม่ได้รับอาหารอาจตายจากความหิวในประมาณ 6.45 วัน ซึ่งอยู่ภายในช่วงพึ่งแม่ จึงต้องตรวจว่าการดูแลที่ทำได้จริงรักษาสุขภาพและการรอดได้ก่อนเทรนหลายรุ่น

# ข้อกำหนดปัจจุบัน: บ้าน งาน และการดูแลข้ามรุ่น

แก้ในโปรเจกต์ #3 และ Notebook เดิม ไม่สร้างโปรเจกต์หรือ Notebook แยก เก็บ Run ทุกครั้งใต้ outputs/run_<timestamp>_<arm>_<seed>/ ตามเดิม ผลเก่ายังคงอยู่และมี source สำรองก่อนแก้ใน outputs/archive/survival_v1_source.zip

## 1. คำถามวิจัย

แนวโน้มดูแลผู้ที่พึ่งพาตนเองไม่ได้สามารถเกิดและส่งต่อผ่านการคัดเลือกหลายรุ่นได้หรือไม่ เมื่อแม่ต้องจัดเวลาให้เป้าหมายส่วนตัวคือการทำงานด้วย การทดลองนี้จำลองแนวโน้มการดูแล ไม่ยืนยันสัญชาตญาณหรือความเป็นแม่ทางชีววิทยาโดยตรง

## 2. Environment

บ้าน 7×5, แม่หนึ่งตัวและลูกหนึ่งตัวต่อโลก แต่ละครอบครัวแยกสถานะกัน มีจุดอาหารพร้อมหยิบ เตียง โต๊ะทำงานหนึ่งจุด พื้นที่เล่น เฟอร์นิเจอร์หนึ่งช่อง และจุดเสี่ยงเล็กน้อยที่ไม่ติดโต๊ะทำงาน ตำแหน่งครัว/โต๊ะสุ่มจากตำแหน่งบ้านที่กำหนดไว้ ไม่มีความหนาว การรออาหารเกิดใหม่ เงินซื้ออาหาร โควตางาน หรือเส้นตายงาน

อาหารหยิบได้แน่นอนถ้าอยู่จุดอาหาร ถือไม่เต็ม และถึงวัยที่ทำได้ ไม่ใช้ความน่าจะเป็นในการหยิบอาหาร ความสำเร็จในการพึ่งตัวเองจึงประเมินจากการเลือกเดินไปหยิบ กิน และพัก ไม่ตีความค่า forage ซึ่งเป็นตัวชี้วัดประสบการณ์หยิบอาหารเพียงอย่างเดียวว่าพึ่งตัวเองได้แล้ว

Episode ปกติ 20 วัน วันละ 200 joint Steps รวม 4,000 Steps; หนึ่ง Step แม่และลูกเลือกอย่างละหนึ่ง action จากสถานะก่อนเวลาเดียวกัน โลกขยับเวลาเพียงครั้งเดียว กติกาสังคมใช้ระยะและ consent ก่อน action เสมอ

## 3. สถานะและพัฒนาการ

หน้าจอแม่และลูกแสดง Health / Food / Fatigue / Stress ครบเหมือนกัน Food ใช้ค่า energy ภายในระบบ (ความอิ่ม/พลังงาน 0–100) และ Food items แสดงจำนวนอาหารที่ถือ แยกจากแถบ Food ค่า cold คงเป็นศูนย์เพื่อรองรับ snapshot readers ภายใน ไม่ใช้เป็นโจทย์

อายุต่ำกว่า 5 วัน ลูกหยิบอาหารเองไม่ได้และเดินช้า; อายุ 5–ก่อน 12 วันเริ่มทำเองและมี skill cap 0.6; ตั้งแต่ 12 วัน cap 1.0 แม่มองเห็นอายุลูกเมื่ออยู่ในระยะมองเห็น เพื่อแยกความช่วยเหลือตามวัย

สุขภาพเสียเมื่อความอิ่มต่ำกว่า 20, Fatigue มากกว่า 90 หรือ Stress มากกว่า 90 ต่อเนื่องเกิน 40 Steps อาการแต่ละอย่างมี timer แยก หากดีขึ้น timer ของสาเหตุนั้นเริ่มใหม่ แยก damage และ death_cause เป็น hunger / exhaustion / stress / hazard การตายถาวรใน Episode นั้น; D มีการเริ่ม Episode ใหม่ของ baseline แม่เดิมตามกติกาเฉพาะ

ค่าตั้งต้น: แม่ใช้พลังงาน 0.03 ต่อ Step; ลูก 0.06 / 0.05 / 0.04 ตามวัย; มื้ออาหารเพิ่ม 30; hunger damage 0.025 ต่อ Step หลัง grace; exhaustion/stress อย่างละ 0.005; hazard damage 0.5 ทุก 50 Steps ขึ้นกับทักษะหลีกเลี่ยง

## 4. Actions และ Reward

20 actions: เดินสี่ทิศ, WAIT, GATHER (หยิบอาหาร), EAT, REST, FEED, SOOTHE, WARN, CALL, OFFER, ACCEPT, REFUSE, CARRY, RELEASE, PRACTICE, WORK, PLAY

WORK ใช้ได้เฉพาะแม่ที่โต๊ะ มีพลังงานมากกว่า 20 และ Fatigue น้อยกว่า 85 ได้ +0.015 ใช้พลังงานเพิ่ม 0.01 และ Fatigue เพิ่ม 0.12 ต่อ Step ที่ทำงานสำเร็จ PLAY ใช้ได้เฉพาะลูกที่พื้นที่เล่นและไม่ได้ถูกอุ้ม ลด Stress เพิ่ม Fatigue เล็กน้อย REST ใช้ได้ทุกจุด แต่เตียงฟื้นความเหนื่อยเร็วเป็นสองเท่าและลด Stress

Reward ส่วนตัวต่อ Step:

```text
(0.01 - 0.005 × (1 - energy/100) - 0.002 × fatigue/100) × alive
+ successful_work_bonus
- 0.2 × health_lost/100
- 5 × death_this_step
```

ไม่ให้โบนัสโดยตรงจาก FEED / SOOTHE / CARRY ไม่มี action สอนทักษะโดยตรง ลูกพัฒนาผ่านการลงมือทำและฝึกเอง การช่วยทุกครั้งจึงไม่ใช่ผลสำเร็จโดยอัตโนมัติ เก็บ effective/unneeded feeds, forced carries และ safe refusal overrides แยก

## 5. Agent และการเรียนรู้

PPO แยกแม่และลูก ใช้ collector นาฬิกาเดียว ไม่ใช้ PPO.learn() เลื่อนโลกแยกกัน default rollout 128, minibatch 64, epochs 4, learning rate 1e-4, gamma .99, GAE .95 และ hidden 32×32

Observation มี own 13, social 10, signals 8, sound direction 3, local 5×5×7 รวม 209 ค่า แล้วต่อ latent z 4 ค่า ช่อง local คือ blocked / food / bed / risk / other-agent / desk / play-area เห็นรอบตัว 2 ช่อง ได้ยินระยะ 4 ช่อง social รวมอายุอีกฝ่ายเมื่อมองเห็น

phi เป็น recurrent map ของ observation กับ z ที่ตรึงในชีวิตและวิวัฒน์ได้ z เปลี่ยนระหว่างใช้ชีวิต ไม่มีการรับประกันว่า z มีบทบาทเชิงสาเหตุครบถ้วนจากการมีตัวแปรนี้เพียงอย่างเดียว

เมื่อ buffer เต็ม ตาย หรือถึงขอบ Episode ใช้ข้อมูลที่สะสมจริงทั้งหมด รวมถึง tail หนึ่ง transition สร้าง buffer ชั่วคราวตามจำนวนจริง ไม่ pad/ทำซ้ำหรือทิ้งโทษตาย Death มี zero bootstrap ส่วนลูกที่ยังรอดที่ขอบ Episode ใช้ value bootstrap เพราะอาจมีชีวิตต่อเป็นแม่ ไม่ flush ตอน Stop กลาง Episode เพื่อเก็บ buffer/optimizer/RNG สำหรับ resume โดยไม่เปลี่ยนลำดับการฝึก

## 6. การสืบทอดและกลุ่มเปรียบเทียบ

A = Baldwinian + PPO + fitness selection; B = PPO + uniform selection ในลูกที่รอด (ยังมี survival selection); C = evolution แต่ปิด PPO โดย physical practice และ z ยังเปลี่ยน; D = PPO แม่เดิมหลาย Episode ไม่มีสืบทอดและ reset physiology ตอนเริ่ม Episode ถัดไป

Genome คือ actor ก่อนเรียนและ phi Learned weights ของแม่ไม่ส่งให้ลูก ลูกเริ่มด้วย genome ของแม่ที่สุ่มปรับ จากนั้นเรียนรู้ชีวิตของตัวเอง ลูกที่รอด 20 วันเป็นผู้สมัครแม่รุ่นถัดไป เก็บประสบการณ์และร่างกายของลูกที่เติบโตนั้นต่อ เมื่อถูกเลือกซ้ำเป็นการแตกแขนงจำลองพร้อม RNG แยก ไม่ใช่ลูกหลายตัวในครอบครัวเดียว

Fitness = child_alive × (0.7 + 0.3 × solo_score) Solo score มาจาก frozen probes หยิบและกินอาหาร กับพักที่เตียง หลังจบวัยลูก ใช้เพื่อคัดเลือกใน train ไม่ใช่ Zero-shot score

ถ้าลูกตายหมดใน A/B/C ให้ประเมินรุ่นนั้นให้เสร็จ บันทึก extinct และหยุด ไม่คืนชีพ ไม่เริ่ม seed ใหม่แทน ผู้ใช้เห็นสถานะและจำนวนรุ่นที่ทำได้ชัดเจน

## 7. Zero-shot ทุกรุ่น

A0 ใช้ genome ก่อนเรียนในชีวิต; A1 ใช้น้ำหนักที่ผ่านวัยลูกก่อนเลี้ยงลูกตัวเอง; A2 ใช้น้ำหนักหลังเป็นแม่ รุ่นแรก A1 เป็น founder baseline ซึ่งไม่มีวัยเด็กจริง

ทดสอบสำเนาแต่ละสถานการณ์ด้วยน้ำหนักตรึง ล้าง z และแยก RNG ไม่เรียก record/train ระหว่างทดสอบ ใช้ matched physical skills เป็นผลควบคุมหลัก Native skills เป็นผลประกอบ ไม่ใช้คะแนนนี้คัดเลือกพันธุกรรม

สถานการณ์เริ่มลูกแรกเกิดทุกกรณี: hungry, afraid_not_hungry, tired_silent, blocked_route, competing_work, false_cry เริ่มต้น Episode ส่วน dangerous_request, safe_refusal, independent_child เกิดตามกำหนดอายุ 12 วัน รายละเอียดการประเมินฉบับปรับปรุงอยู่ท้ายเอกสาร

Monitor แยก seeds จาก train; holdout เป็นแผนที่สะท้อนซ้ายขวาพร้อม seeds แยก สะท้อนโต๊ะและพื้นที่เล่นด้วย ยังไม่ครอบคลุมทุกสถานการณ์จริง ห้ามใช้ monitor/holdout scores เป็น fitness และควรล็อกการออกแบบก่อนเปิดผลสรุปสุดท้าย

## 8. ผลและกราฟ

metrics.csv บันทึกต่อครอบครัวต่อรุ่น; development.csv รายวัน; evaluations.csv ราย Zero-shot; manifest.json สถานะและ config/source/dependencies; checkpoint รวมประชากรและ RNG

ดู survival, สุขภาพเฉลี่ยตลอด Episode, solo success, ความอิ่ม/เหนื่อย/เครียดตามอายุ, work steps/reward, work while child needy, อาหารที่ส่งให้ลูก, damage แยกสาเหตุ, การช่วยเกินจำเป็น และ Zero-shot A0/A1/A2 รวมผลตอบสนองต่อความต้องการเฉพาะ (พลังงาน/ความกลัว/ความเหนื่อยเปลี่ยนเท่าไร)

Counts การช่วยเป็น descriptive ไม่ใช่คะแนนความเหมาะสมโดยลำพัง รวมผลข้ามรันโดย independent seeds ไม่ใช้ Agent หลายตัวในประชากรเดียวเป็น independent experiments เปรียบเทียบเฉพาะกติกาและงบที่ตรงกัน

## 9. การใช้งานและสถานะการตรวจ

แก้ไฟล์เดิมทั้งหมด ไม่สร้างอีก Notebook ทุกงานเริ่มจากปุ่ม เซลล์ Setup/Config/panels ไม่เดิน simulation ไม่สร้างโมเดล ไม่ติดตั้งหรือเทรนเอง UI เป็นภาพ PNG อัปเดต Image widget เดิมใน Notebook ไม่มีหน้าต่าง Simulation แยก View Calm/Flow/Fast หน่วงการส่งภาพ .10/.03/0 วินาที จึงมีผลต่อ wall-clock แต่ไม่เปลี่ยนกติกา

รหัส compatibility ภายในคือ maternal-house-v2.0 เพื่อปฏิเสธ checkpoint กติกาเก่าที่มี observation/action ต่างกัน ไม่ใช่โปรเจกต์หรือโฟลเดอร์ทดลองแยก หน้ารายงานดู Run เก่าได้แต่ไม่รวมผลต่างกติกา โมเดลเก่าโหลดต่อเป็นบ้านไม่ได้

ยังไม่ได้รัน simulation, training, unit tests หรือ oracle feasibility ของกติกาบ้าน ค่าปัจจุบันเป็นค่าตั้งต้น ผ่านได้เฉพาะการตรวจ static/schema และภาพนิ่ง ก่อนสรุปวิจัยต้องทดสอบว่า (1) ผู้ดูแลเหมาะสมทำให้รอดได้ (2) ละเลยมีผลเสีย (3) ช่วยเกินจำเป็นมีต้นทุน (4) ข้อมูลท้ายชีวิตไม่ถูกทิ้ง และ (5) มีโอกาสผ่านรุ่นแรกจริง ใช้ pilot 16×20, main 64×100 หลาย seeds; smoke 2×2 และย่อ Episode เหลือ 2 วัน ตรวจโค้ดเท่านั้น

## การปรับการประเมิน 24 ตุลาคม 2026

- Zero-shot เลี้ยงลูกครบ Episode เท่าตอนฝึก: pilot/main 20 วัน × 200 Steps = 4,000 Steps โหมด smoke ใช้ชีวิตย่อเท่าการฝึกของโหมดนั้น `eval_steps` ปรับตาม `world.horizon` โดยอัตโนมัติ ส่วน solo fitness probes ยังคงสั้นและใช้คัดเลือกใน train เท่านั้น
- ทุกสถานการณ์เริ่มลูกแรกเกิดและทักษะเริ่มต้นศูนย์ ใช้คู่ทดสอบแบบเขียนกฎเหมือนกันระหว่างโมเดล เพื่อควบคุมความแตกต่างของลูก ไม่ได้ให้แม่ลอกพฤติกรรม ไม่มี PPO หรือการฝึกทักษะระหว่างข้อสอบ แต่ความสามารถตามวัยเปิดตามกติกาเดิม (ก่อน 5 วัน, 5–12 วัน, ตั้งแต่ 12 วัน)
- ย้ายอาหาร เตียง โต๊ะ และจุดเล่นไปตำแหน่งนอกชุดฝึก โดยมีจำนวนจุดหลักเท่ากติกาปริยายเดิม ลูกหิว/กลัว/เหนื่อยแต่เงียบ/แม่กำลังทำงาน/เสียงร้องหลอกเกิดต้น Episode ส่วนคำขอเสี่ยง การปฏิเสธ และทำเองได้ เกิดเมื่ออายุ 12 วัน ไม่กระโดดข้ามวัย หากเป็น smoke ชีวิตสั้นจะวางเหตุการณ์ช่วงวันสุดท้ายเพื่อ debug เท่านั้น จึงไม่ใช้สรุปพัฒนาการตามวัย
- สถานการณ์พิเศษยาวหนึ่งวัน หลังจากนั้นลูกกลับใช้กฎดูแลตัวเองตามวัย ลูกเหนื่อยแต่เงียบสามารถพักได้เมื่อแม่พาไปเตียง ไม่ถูกสั่ง WAIT ตลอดชีวิต ไม่มีการชุบชีวิตลูกที่ตายก่อนเหตุการณ์
- A0 ใช้น้ำหนักแรกเกิดที่สืบทอด ไม่ใช้การเรียนรู้ทั้งวัยลูกและช่วงเป็นแม่ A1/A2 เป็นผลประกอบ แม่ตัวเดิมและ scenario seeds จับคู่กันในแต่ละ phase; run_seed คือการรันกระบวนการทดลองอิสระ คนละความหมายกับ scenario_seed และคนละความหมายกับกลุ่ม A/B/C/D
- เพิ่ม `no_help` (แม่ใช้กฎดูแลตัวเอง/ทำงาน ไม่เลือก social care) และ `always_help` (กฎให้ความสำคัญกับการช่วยและอุ้มซ้ำแม้ไม่จำเป็น ยังมีการกินของตัวเองและการเคลื่อนที่) เป็นจุดอ้างอิง ไม่ใช่โมเดลที่เทรนเพิ่ม ไม่ใช่คู่เหมือนที่เปลี่ยนแค่หนึ่ง Action จึงยังไม่ใช่การพิสูจน์เชิงสาเหตุที่สมบูรณ์ ทั้งสองใช้ใน A0/normal เท่านั้นเพื่อไม่รันซ้ำทุก phase
- บันทึก Health/ความต้องการ/การเก็บอาหารเองแยกช่วงวัย รวมแม่รอด ลูกรอด รอดทั้งคู่ การช่วยที่ตรงเป้าหมายเบื้องต้น การช่วยที่ไม่มีความต้องการเป้าหมาย และการฝืนปฏิเสธ วัดผลตอบสนอง 20 Steps หลังเริ่มเหตุการณ์แยกจากผลปลายวันและผลครบชีวิต จึงไม่ใช้ความเปลี่ยนแปลงปลาย 20 วันแทนการตอบสนองทันที
- `appropriate_help_attempts` / `unnecessary_help_attempts` เป็นตัวชี้วัดตาม threshold ของอาหาร ความกลัว และความเหนื่อย ยังไม่ใช่คำตัดสินความเป็นแม่ ต้องอ่านควบคู่กับผลที่เกิดกับลูก การยินยอม และกรณีควบคุม การทำให้ความต้องการดีขึ้นเองหรือจากกฎของลูกอาจเกิดได้ จึงต้องเทียบ no_help ด้วย ไม่ใช้การช่วยบ่อยเป็นหลักฐานเพียงอย่างเดียว
- กราฟหลักใช้ A0 normal แยก monitor/holdout และ matched/native; กราฟการฝึกและ A1/A2 เป็นข้อมูลประกอบ ไฟล์สรุปหลัก `plots/a0_*_summary.csv` และแยกสถานการณ์ `plots/a0_*_by_scenario.csv` เมื่อกด Build run report; Compare selected ใช้ monitor/matched เป็นหลัก เฉลี่ยภายใน Run ก่อน bootstrap ข้าม Run seeds ไม่ถือว่าครอบครัวในประชากรเดียวเป็นการทดลองอิสระ
- Health ตามช่วงวัยนับเวลาหลังตายด้วย ไม่ตัดความล้มเหลวทิ้ง ช่วงวัยที่ smoke ไปไม่ถึงใช้ -1 ไม่ใช่สุขภาพศูนย์ กราฟข้ามรุ่นที่ไม่มีโมเดลเพราะสูญพันธุ์ไม่แต่งค่า A0 ขึ้นมา ต้องอ่านจำนวน Run ที่เหลือใน CSV คู่กับผลการสูญพันธุ์จาก train
- ผลเก่า 200 Steps และ checkpoints เดิมไม่ถูกแก้ไข การกดประเมินใหม่เขียน `evaluations_full_lifetime_*.csv` พร้อม JSON อธิบายที่มาและสถานะ รายงานหลักไม่รวมไฟล์ที่หยุดกลางงานหรือผลคนละระยะเวลา ไฟล์เดิมยังเป็นหลักฐานข้อสอบสั้นตามจริง
- checkpoint บ้านเดิมที่ตรงรายการ hash ของ policy/physics/inheritance ที่รู้จัก ใช้ทดสอบแบบ frozen กับข้อสอบใหม่ได้ โดยไม่ต้องเทรนใหม่ แต่การ Resume training ยังตรวจ source hashes แบบเข้มงวดและไม่ผสมข้อสอบเก่ากับใหม่ใน Run เดิม
- ไม่ได้เพิ่ม Fine-tune งานใหม่ ไม่แก้ reward/physics/ช่วงวัยที่ใช้ฝึก และไม่เริ่มเทรน ประเมิน Simulation หรือ unit tests อัตโนมัติ หลังแก้ตรวจเฉพาะโครงสร้างและ syntax ผล runtime และความสมดุลยังต้องตรวจเมื่อผู้ใช้สั่งรัน

### วิธีใช้หลังอัปเดต

1. เปิด Notebook เดิม แล้ว Restart Kernel เลือก Python 3.12 (Maternal #3) รัน Setup และ Config ก่อนสร้างหน้าควบคุมใหม่
2. หากต้องการใช้โมเดลที่ฝึกไว้ กรอก checkpoint ของรุ่นที่จบแล้วในหัวข้อ 6 เลือก normal + monitor + matched แล้วกด Start evaluation ด้วยตนเอง ทำทีละ checkpoint ของ Generation ที่ต้องการสรุป ไม่ได้ประเมินทุก checkpoint อัตโนมัติ
3. หลังประเมินเสร็จ ไปหัวข้อ 7 กด Refresh runs แล้ว Build run report หรือ Compare selected เมื่อมีผลครบใน Run ที่เลือก
4. ผลเดิมเปรียบเทียบได้เฉพาะข้อสอบสั้นเดิม ต้องมีผลใหม่ก่อนอ่านกราฟ A0 แบบเต็มชีวิต การประเมิน 4,000 Steps ใช้เวลามากกว่าเดิม และมีจุดอ้างอิงอีกสองแบบ

การเลือกอุปกรณ์: device มีค่าเริ่มต้นเป็น auto ตรวจ torch.cuda.is_available() เมื่อกดเริ่มงาน หากใช้ CUDA ได้ PPO จะใช้ CUDA ไม่เช่นนั้นใช้ CPU พร้อมแสดง Device ใน log ใช้หลักการเดียวกันกับการรันต่อ การดูโมเดล และการประเมินแบบ frozen ตัว Grid World การสุ่ม Action และกลไกภายในที่ตรึงไว้ยังทำงานบน CPU การใช้ CUDA ต้องเป็น PyTorch ที่รองรับ CUDA ไม่ได้ติดตั้งหรือเปลี่ยนแพ็กเกจให้อัตโนมัติ บันทึกอุปกรณ์จริงใน config/manifest หรือ metadata ของการประเมิน การเปลี่ยนอุปกรณ์อาจทำให้ตัวเลขไม่ตรงกันทุกบิตแม้ใช้ Seed เดิม
