# การทดลองปัจจุบัน: Model A — Rewarded PPO + Baldwinian Evolution

คำถาม: ผล Zero-shot ก่อนประสบการณ์เลี้ยงลูกของแม่แต่ละรุ่นดีขึ้นตาม Generation หรือไม่? ใช้ Model A อย่างเดียว หลาย Seed เป็นการทดลองอิสระ ไม่มีการเปรียบเทียบ B/C/D ใน protocol นี้

กติกา `maternal-house-v3.1-effective-care-reward`; ข้อสอบ `full_lifetime_care_v10_effective_care` ต้องเริ่ม Run ใหม่ ห้าม Resume checkpoint เก่า หรือรวมผลข้ามกติกา ผลใหม่อยู่ `outputs/2_model/run_...` ผลเก่าเก็บที่เดิม

- แม่หนึ่งตัว ลูกหนึ่งตัว Grid 7×5 Episode 20 วัน × 200 joint Steps ไม่มีงานแม่ ลูกเดินทุก 5/3/1 Steps ตามวัย การหยิบอาหารช่วง 7–14 วันต้องมีแม่อยู่ใกล้และ OFFER ความหิวลูกเสีย Health 0.14/Step หลัง Food <20 เกิน 40 Steps เหมือนเดิม
- ทุกครอบครัวฝึก PPO ด้วย Reward ดูแลตัวเองเดิม บวก Reward ดูแลลูกให้แม่ที่ยังมีชีวิต: ผลจากการช่วยจริง + maintenance เล็กน้อย − ความต้องการค้าง − Health ที่เสีย − การตาย + โบนัสรอดเมื่อจบ Episode ตามสูตรล่าสุดด้านล่าง
- `welfare = (Health/100) * min(Food/40, 1) * (1-Fatigue/100) * (1-Fear/100)`; ลูกตาย welfare=0 ไม่ให้โบนัสจากจำนวน FEED/CARRY จึงยังต้องอ่านผลสุขภาวะและการแทรกแซงเกินจำเป็นประกอบ
- บันทึก `mother_care_reward` แยกจาก reward เดิม ค่าในโลกประเมิน/Balance เป็นศูนย์ ไม่เปลี่ยน Reward ให้ลูก
- เก็บ genome ก่อน PPO ส่งต่อให้ลูกพร้อม mutation ระหว่างสร้างลูก เมื่อผู้รอดที่ได้รับเลือกโตเป็นแม่ให้สร้าง Learner ใหม่จาก genome เท่านั้น ไม่รับ policy/optimizer/latent memory ที่เรียนในวัยเด็ก ร่างกายเริ่มเป็นแม่ด้วย Health100, Food70 และทักษะกายภาพมาตรฐาน0.5/0.3 ไม่มี mutation ซ้ำในจังหวะโตเป็นแม่
- คัดเลือกด้วย Fitness เดิม `child_survival*(0.5 + 0.3*mean_child_health/100 + 0.2*adult_readiness)`; การวัด readiness เป็นข้อสอบฝึกแยกจากชุด Zero-shot หากลูกรอดไม่เหลือหยุด extinct ไม่มีการฟื้นตัวอัตโนมัติ
- ประเมิน A0 เท่านั้นของแม่รุ่นปัจจุบัน: สำเนาจาก genome น้ำหนักตรึง ความจำใหม่ ไม่มี PPO และไม่มี Reward ดูแลลูก บ้านใหม่ครบ20วัน ลูก benchmark ใช้กฎคงที่ ไม่ใช้ผลข้อสอบคัดเลือกพันธุกรรม
- Generation0 = แม่ผู้ก่อตั้งที่ยังไม่มีบรรพบุรุษผ่าน selection; Generation1 = ลูกที่โตเป็นแม่หลังคัดเลือกครั้งแรก เป็นต้น A0 แม้บันทึกหลังจบการเลี้ยงของรุ่นนั้นก็โหลด genome ก่อนเรียน ไม่มีข้อมูลที่เรียนแล้วปะปน หากตั้ง20รุ่นจะได้ Gen0–19 ไม่ใช่ Gen1–20
- ตัวฝึกกับตัวประเมินแยกกัน ไม่ส่งผลประเมินกลับเข้า PPO/selection; A0 ในบ้านใหม่ยังมี state ทางกายภาพและ latent เปลี่ยนระหว่าง Episode ได้ แต่น้ำหนักไม่เปลี่ยน

CSV `a0_*_change_from_gen0.csv` เก็บค่าราย Seed และผลต่าง; `a0_*_run_counts.csv` เก็บจำนวน Seed ที่มีผลในแต่ละรุ่น ไม่เติมผลอนาคตของ Run ที่สูญพันธุ์ ค่าเฉลี่ยรุ่นหลังอาจเอนเอียงเพราะเหลือแต่ Run ที่ไปต่อ ต้องอ่านจำนวน Run/manifest ด้วย รายงานอื่นมีความต้องการค้าง สุขภาพแยกวัย การแทรกแซงเกินจำเป็น และผลแยกสถานการณ์ กราฟ Train เป็นข้อมูลประกอบ ไม่รวมกับ A0

กฎอ้างอิงไม่ช่วย/ช่วยครึ่งวันทุก4วัน/ดูแลเหมาะสม/ช่วยเกินจำเป็น ยังใช้ตรวจโลก ไม่ใช่โมเดลเพิ่ม กลุ่มช่วยเกินจำเป็นปัจจุบันมีข้อจำกัดการจัดอาหาร จึงไม่ใช้พิสูจน์ว่าดูแลมากเป็นโทษ

หลาย Seed ช่วยดูความสม่ำเสมอ แต่อย่างเดียวไม่พิสูจน์ว่า selection จำเป็นหรือแยกผล PPO ออกจาก Evolution และไม่ยืนยันว่าสัญชาตญาณทางชีววิทยาเกิดขึ้น บรรพบุรุษได้รับ Reward ดูแลลูกอย่างชัดเจน

ก่อนใช้งาน: โหลด Notebook ใหม่ → Restart Kernel → Setup → Config → Check balance เมื่อผู้ใช้กดเอง แล้วจึงเริ่ม Train/Batch เอง ข้อ3รัน A Seed0/1/2 รวม3Runs ไม่มีการเริ่มงานอัตโนมัติ กติกาใหม่ยังไม่ผ่านการตรวจ Balance/ฝึกจริง


## Reward ล่าสุด: ให้เครดิตผลจากการดูแล

- ป้อนเพิ่ม Food จริงในช่วงต่ำกว่า50: `0.6*food_relief/meal_energy` ค่าเริ่มต้น meal_energy30; หากให้ถืออาหาร รอจนลูกกินอาหารที่แม่จัดไว้จริง ไม่ให้ตอนส่งของ; ลูกกินอาหารที่หาเองไม่มีโบนัสส่วนนี้
- ปลอบลด Fear ส่วนเกิน60 สำเร็จตาม consent: `0.2*fear_relief/soothe_effect` ค่าเริ่มต้น12
- รักษาสุขภาวะต่อ Step: `0.001*welfare` ลดจาก0.02 (เหลือ1/20) เพื่อยังให้คุณค่ากับการป้องกัน แต่ไม่ให้คะแนนจากสถานะตั้งต้นมากเกินไป
- ลูกยังมีชีวิตแต่ความต้องการค้าง: `-0.005*(max(0,30-Food)/30 + max(0,Fatigue-70)/30 + max(0,Fear-60)/40)`
- Health ลูกเสีย: `-0.02*health_loss`; ลูกตาย `-2` ครั้งเดียว
- ครบ Episode และแม่ลูกรอด: `+2*child_Health/100` ครั้งเดียว ไม่แทนสัญญาณระหว่างชีวิต

ทุกส่วนเปิดเฉพาะ Train; Zero-shot/Balance ไม่มี Reward ดูแลลูก ไม่เพิ่มคะแนนจาก Action ที่ไม่สำเร็จ อาหารเต็มหรือป้อนเมื่อ Food>=50 ไม่มีโบนัสแก้หิว ไม่เปลี่ยน Reward ของลูก อัตราหิว ความเสียหาย Fitness และการสืบทอด

บันทึก `care_reward_food_relief`, `fear_relief`, `maintenance`, `unmet_need`, `damage`, `death`, `survival` (ทุกชื่อมี prefix care_reward_) แยกจากยอด `mother_care_reward` ใน metrics.csv และกราฟประกอบ `training_care_reward.png` แกน X=Generation, Y=Reward สะสมเฉลี่ยต่อครอบครัว กราฟนี้เป็นข้อมูล Train ไม่รวมเป็นหลักฐาน A0

สูตรนี้เป็นข้อเสนอเพื่อให้สัญญาณเรียนรู้ชัดขึ้น ยังไม่ยืนยันว่าฝึกสำเร็จหรือป้องกัน reward exploitation ทุกกรณี ไม่เริ่มเทรน Balance หรือประเมินอัตโนมัติ ต้องใช้ Run ใหม่ และแยกจากผล protocol ก่อนหน้า

โปรเจกต์ Jupyter Notebook แม่หนึ่งตัว–ลูกหนึ่งตัว ในบ้าน Grid World 7 × 5 สีครีม ทดสอบพฤติกรรมดูแลที่แสดงออกจากน้ำหนักแรกเกิดหลังการคัดเลือกข้ามรุ่น


**ข้อตกลงปัจจุบัน:** ลูกค่อย ๆ ช่วยตัวเองตามวัยใน Episode 20 วัน ก่อน 7 วันต้องให้แม่ป้อน; 7–14 วันกินเองและหยิบอาหารเมื่อแม่อยู่ใกล้และส่งสัญญาณ OFFER; ตั้งแต่ 14 วันเริ่มหยิบเองโดยไม่ต้องมีแม่อยู่ใกล้ ลูกที่รอดและได้รับเลือกจึงเปลี่ยนบทบาทเป็นแม่เมื่อขึ้นรุ่นถัดไป ไม่เปลี่ยนบทบาทระหว่าง Episode

**หากแม่ตาย:** ไม่สั่งฆ่าลูกทันที ลูกเล็กยังหาอาหารไม่ได้ ลูก 7–14 วันไม่มีผู้ดูแลให้หยิบอาหารแบบมีคนช่วย ลูกตั้งแต่ 14 วันอาจอยู่ต่อได้หากเดินไปหยิบ กิน และพักเป็น ดู `child_orphan_steps`, `child_died_after_mother`, `orphaned_child_alive_at_end` คู่กับช่วงวัย

อาหารยังไม่จำกัดจำนวน ไม่เพิ่มโรค ความหนาว หรือการสุ่มตาย การปรับรอบนี้ทำให้ผลสะสมจากการละเลยสัมพันธ์กับช่วงวัยมากขึ้น เป้าหมายคือเห็นผลดีของการดูแล ไม่ใช่บังคับให้ตายจำนวนหนึ่ง ยังไม่ได้ยืนยันสมดุลด้วยการรันจริง

ไม่แก้ Reward หรืออัตรา Food ลด แต่เพิ่มความเสียหายจากความหิวเฉพาะลูกจาก 0.08 เป็น 0.14/Step ความสามารถที่เพิ่มตามอายุเป็นกติกา Environment ไม่ใช่หลักฐานว่าแม่สอนหรือพันธุกรรมวิวัฒน์ ต้องตรวจว่ากฎดูแลเหมาะสมให้สุขภาพ/การรอดดีกว่าไม่ช่วย โดยเฉพาะช่วง 0–7 วัน ก่อนอ้างผลหลัก การเปิด Action ให้ลูกยังไม่รับประกันว่าลูกที่ใช้ PPO จะเรียนรู้หยิบและกินได้เอง


ลูกเดินได้ทุก 5 / 3 / 1 Steps ตามวัยก่อน 7 วัน / 7–14 วัน / ตั้งแต่ 14 วัน หาก Fatigue > 85 เพิ่มช่วงรออีก 1 Step แม่เดินเร็วเท่าเดิม

กฎอ้างอิง `light_help` ช่วยเฉพาะ 2/4 วันแรก (ครึ่งวัน) ทุก 4 วัน เวลาที่เหลือดูแลตัวเอง ใช้เทียบกับไม่ช่วย ดูแลตามความต้องการ และช่วยเกินจำเป็น ไม่ใช่โมเดลที่เทรนเพิ่ม กฎนี้เป็นตัวแทนของการดูแลขาดช่วง ไม่ใช่นิยามตายตัวของการดูแลน้อย

การรอดขึ้นกับ Food, Health และความต้องการจริง ไม่สุ่มตายหรือบังคับให้รอดตามจำนวนครั้งที่ช่วย คง Reward และ Food drain; ความเสียหายจากความหิวของแม่ยัง 0.08/Step ของลูกเพิ่มเป็น 0.14/Step ต้องกด Check balance เองเพื่อยืนยันว่าการดูแลทันเวลาและเพียงพอให้ผลดีกว่าละเลยหรือช่วยขาดช่วง ยังไม่รับรองอัตรารอดหลังแก้โค้ด


การปรับสมดุลรอบนี้เปลี่ยนเฉพาะความเสียหายจากความหิวของลูก 0.08 → 0.14/Step (+75%) หลัง Food ต่ำกว่า 20 ต่อเนื่องเกิน 40 Steps ทุกวัยใช้ค่าเดียวกัน ทั้ง Train และ Zero-shot แม่ยัง 0.08/Step การดูแลก่อนถึงเงื่อนไขนี้ไม่เสีย Health จากความหิว กฎ light_help และกฎอ้างอิงอื่นคงเดิม ค่านี้เป็นค่าทดลอง ยังไม่ได้ยืนยันอัตรารอดด้วย Balance ห้ามรวมผลกับกติกาเก่าหรือ Resume checkpoint เก่า

## กลุ่มทดลอง

| กลุ่ม | ระหว่างชีวิต | การขึ้นรุ่นถัดไป |
|---|---|---|
| A | PPO | ถ่วงโอกาสคัดเลือกลูกที่รอดตาม Fitness; ถ่ายทอดน้ำหนักแรกเกิด + สุ่มปรับ |
| B | PPO | สุ่มในลูกที่รอดเท่าเทียม; ส่งต่อเหมือน A ยังมีการกรองด้วยการรอด |

## Multi-core สำหรับ Intel Core Ultra 7 155H

Notebook ที่สร้าง Config ผ่าน `ExperimentConfig.profile(...)` เริ่มต้น Backend **Multi-core CPU** และ **Workers 4** สำหรับเครื่อง 155H / RAM 16 GB นี้ โดยลดลงเมื่อมีครอบครัวน้อยหรือระบบเปิดให้ใช้ CPU น้อย แต่ละ Process มี Torch/SB3 runtime ของตัวเอง จึงใช้ RAM เพิ่ม เลือก 4 เป็นจุดเริ่มต้นเพื่อเผื่อ RAM ให้ Notebook และระบบ ไม่ได้อ้างว่า benchmark แล้วว่าเร็วที่สุด ไม่ล็อก affinity ว่าต้องเป็น P-core หรือ E-core ระบบปฏิบัติการเป็นผู้จัดสรร Core เอง เลือก View → Off เพื่อลดการสร้างภาพได้ หากเครื่องร้อนหรือ RAM ตึงให้ลด Workers เป็น 2 หาก RAM เหลือและวัดแล้วเร็วขึ้นจึงลอง 6 ใน Run ใหม่

แต่ละ Process ทำงานได้ข้ามข้อจำกัด Python GIL มีโมเดล optimizer rollout ความจำ และ RNG ของ Agent แยกกันทั้งหมด ใช้ `spawn` ทั้ง Windows และ Linux และจำกัด PyTorch/BLAS ที่ 1 thread ต่อ Process ลดการแย่ง Core โมเดลอยู่ใน worker ตลอดช่วง care ไม่ส่งน้ำหนักทุก Step ส่งเฉพาะ Progress และ snapshot ภาพทุก `process_chunk_steps` (ปริยาย 128 joint steps ต่อครอบครัว) ตัวเลขนี้ควบคุมการรายงานและจุดพัก ไม่เปลี่ยนขอบเขต PPO rollout หรือการอัปเดตน้ำหนัก

Pause/Stop ระหว่างฝึกรอให้ทุก worker ในรอบปัจจุบันเสร็จ จากนั้นย้าย world, policy, optimizer, rollout ที่ยังไม่เต็ม และสถานะ RNG กลับ coordinator ก่อนเซฟ Resume สร้าง Processes ใหม่และโหลดสถานะเหล่านั้น หาก worker ล้มเหลวหรือไม่ตอบสนองจะแสดง error ไม่เซฟสถานะที่เก็บมาไม่ครบ และไม่ลองเทรนใหม่อัตโนมัติ เฉพาะ coordinator เขียนไฟล์ Run Fitness ที่ใช้คัดเลือกและ Arms/Seeds แต่ละ Job ยังรันเรียงกัน ส่วน Zero-shot กระจายตามกรณีดังต่อไปนี้

### Zero-shot แบบ Multi-core

Backend Multi-core CPU ใช้ Workers เดียวกันกระจายกรณี Zero-shot ในแต่ละ phase (A0/A1/A2) อัตโนมัติ แต่ phase ยังเรียงกัน กรณีทดสอบและการตรวจ self-care ที่ประกอบผล Zero-shot ใช้ CPU process แยก ใช้สำเนาซึ่งแยกจากโมเดลฝึก ตรึงน้ำหนัก เริ่มความจำใหม่ และใช้ scenario/action seeds เดียวกับ Serial ทุกกรณี ไม่เพิ่ม gradient, PPO update หรือการเรียนรู้ใด ๆ ไม่เปลี่ยนข้อสอบหรืออายุการทดสอบ (ยังเต็ม 20 วัน/4,000 Steps ตาม Config)

coordinator เก็บ CSV ตามลำดับ candidate/scenario/seed/intervention/policy เดิม ไม่ใช้ลำดับที่งานเสร็จมาจัดผล ภาพและ Progress อัปเดตเมื่อกรณีหนึ่งจบ แสดงโลกสุดท้ายของกรณีนั้น จึงไม่ใช่ภาพสดทุก Step ขณะ Pause กรณีที่ส่งไปแล้วอาจจบใน worker แต่ไม่ส่งงานเพิ่ม Stop ส่งสัญญาณให้ worker หยุดในการตรวจ Step ถัดไป กรณีที่ทำไม่ครบไม่ถูกเขียนเป็นผลสมบูรณ์ กรณีที่คำนวณล่วงหน้าแต่ยังไม่ได้ส่งผลให้ coordinator จะถูกทิ้งเมื่อ Stop

หัวข้อ 6 ประเมินเพิ่มมี Checkbox **Multi-core CPU** และช่อง **Workers** ของตัวเอง หากต้องการเทียบ Serial ใช้ `CONFIG.parallel_zero_shot = False` ก่อนสร้างหน้าฝึก หรือเอาเครื่องหมายออกในหัวข้อ 6 ไม่ต้องเปลี่ยนโมเดล มีชุดตรวจเทียบผลและการยกเลิกสำหรับรันเอง: `python -m unittest tests.test_parallel_evaluation -v` ยังไม่ได้รันทดสอบหรืออ้างว่าผลตรงกันจริงทุกบิตบนทุกเครื่อง

### ลดงานคำนวณซ้ำใน D และ Zero-shot

ทุกกลุ่มใช้เส้นทาง Multi-core เดียวกัน ไม่มีข้อยกเว้นให้ D ต้องรัน Serial เวลารวมอาจต่างกันมากเพราะ A/B/C ยุติเมื่อไม่มีลูกที่รอด ส่วน D เป็นกลุ่มแม่เดิมเรียนรู้ต่อเนื่อง จึงทำครบรอบที่ตั้งไว้แม้ไม่มีลูกรอด ต้องเทียบเวลาใน Phase/Generation เดียวกันและจำนวนข้อสอบที่ทำจริง ไม่ใช้เวลารวมที่ Run สูญพันธุ์เร็วมาเทียบตรง ๆ

D นำโมเดลแม่และ optimizer เดิมไปใช้ในรอบถัดไปโดยไม่สร้าง PPO ใหม่เมื่อมีแม่ครบอยู่ในหน่วยความจำ หาก Resume ช่วงสร้างประชากรค้างไว้จะโหลดจาก state ตามเดิม ไม่เปลี่ยนกติการีเซ็ตสภาพร่างกาย การเรียนรู้ หรือการส่งต่อน้ำหนัก การเทรนยังใช้ `choose()` แบบเดิม

Frozen evaluation ใช้ `act()` ซึ่งคงการคำนวณ actor, internal state และการสุ่ม Action เดิม แต่ข้าม critic และ log probability ที่ไม่มีการนำไปใช้ฝึก Worker เก็บโมเดลสำเนาส่วนตัวต่อ candidate/phase เพื่อลดการสร้าง PPO ซ้ำ ก่อนทุกข้อรีเซ็ต z และ Action RNG ตาม Seed เดิม ไม่มีการนำความจำหรือประสบการณ์จากข้อก่อนหน้ามาใช้ และไม่ใช้ actor เดียวกันประเมินสองข้อพร้อมกัน ยังไม่ได้ benchmark หรือรัน regression checks เพื่อยืนยันผลเทียบเดิม

ไม่มีการเริ่ม worker ตอน import, เปิด Notebook หรือสร้างหน้าควบคุม เริ่มเฉพาะเมื่อผู้ใช้กด Start ไม่ต้องติดตั้งแพ็กเกจเพิ่ม หลังแก้โค้ดต้อง Restart Kernel และสร้าง Config/หน้าควบคุมใหม่ มี regression checks สำหรับรันเอง: `python -m unittest tests.test_processes -v` (มี PPO updates สั้น ๆ) ยังไม่ได้รันหรือวัดความเร็วบนเครื่องจริง

## โหมด Serial และ Threads

หน้าควบคุมเทรนงานเดียวและ Batch มีช่อง **Backend / Workers** เลือก Serial เพื่อใช้ลำดับเทรนเดิม หรือ Threads พร้อม Workers 2/4 เพื่อใช้หลาย thread ใน Process เดียว หากต้องการทั้งลำดับและตัวสุ่มแบบ legacy ให้สร้าง `ExperimentConfig()` และตั้ง Backend Serial, Workers 1, `ppo_shuffle_rng="legacy"` ก่อนสร้างหน้าควบคุม ส่วน Config จาก profile ใช้ตัวสุ่ม per_agent เพื่อรองรับ Multi-core

ทุก Backend ไม่รวมประสบการณ์ข้ามครอบครัว ไม่เปลี่ยน reward จำนวนวัน จังหวะอัปเดต PPO fitness หรือการคัดเลือก เมื่อใช้ Processes หรือ Workers > 1 ระบบเปลี่ยน PPO shuffle เป็น `per_agent` และเซฟสถานะตัวสุ่มนี้ใน checkpoint เพื่อไม่แย่งใช้ NumPy RNG ร่วมกัน นี่ต่างจาก RNG ของ Run เก่า จึงไม่รับประกันว่า Seed เดิมให้ผลเท่าเดิม หากต้องการตรวจเทียบ Backend ให้ใช้ `CONFIG.device="cpu"` และ `CONFIG.ppo_shuffle_rng="per_agent"` เหมือนกันทุก Backend บนอุปกรณ์เดียวกันก่อนเก็บผลหลัก

ใน Backend Threads Worker ทำครั้งละไม่เกิน 16 joint steps ต่อครอบครัว แล้วรอให้ทุกงานในรอบเสร็จก่อนอัปเดต Progress, Pause, Stop & save หรือเข้า assessment การเซฟไม่มี worker ค้างแก้โมเดลอยู่ Resume ใช้ Backend/Workers และตัวสุ่มจาก config ของ Run นั้น การตรวจ fitness ยังรันเรียงกัน Zero-shot ใช้ Processes เฉพาะ Backend Multi-core CPU และเปิด parallel_zero_shot

Python 3.12 ยังมี GIL และ GPU มีต้นทุนรับส่งข้อมูล จึงยังไม่อ้างว่าเพิ่ม Threads แล้วเร็วขึ้น ต้องวัดบนเครื่องจริง โค้ดใหม่นี้เปลี่ยน source hashes: checkpoint จากโค้ดเก่าจะไม่ผ่าน exact-resume ให้เก็บโค้ดเดิมไว้คู่กับ Run เก่า ไม่แก้ manifest เพื่อข้ามการตรวจ เพิ่ม regression checks ไว้สำหรับรันเอง แต่ยังไม่ได้เริ่มเทรนหรือทดสอบความเท่ากันจริง
